# Changelog

All notable changes to `tickwise-ffi` are documented in this file. The C surface is versioned separately from the Rust crates; see the ABI versioning section of the README.

The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [Unreleased]

### Added
- Pass 2 over the C ABI. The dump builder, `tickwise_dump_new`, `tickwise_dump_destroy`, `tickwise_dump_clear`, `tickwise_dump_len`, and one `tickwise_dump_set_*` per value type plus `tickwise_dump_set_len` for collection lengths, assembles a state dump field by field on the engine's side. The replayer, `tickwise_replayer_open` through `tickwise_replayer_destroy`, hands each recorded step's inputs to the caller, verifies pushed hashes against the recording, collects dumps at the ticks named at open, exposes `nearest_snapshot_before` and `seek_to`, and writes a `.dump` at finish. A `MissingDump` leaves the step pending so the call can be repeated with the dump; a protocol slip at finish leaves the session alive.
- `dump_interval` in `TickwiseRecorderConfig`, `tickwise_recorder_wants_dump`, and `tickwise_recorder_record_dump`, so a recording carries state dumps every N ticks and on demand, and `tickwise diff a.rec b.rec` reaches field level with no replay.
- Status codes `HashMismatch`, `InputFormatMismatch`, `TickOutOfRange`, `ProtocolMisuse`, `MissingDump`, and `EmptyRecording`.
- The C harness now runs both passes: it records with a dump every 100 ticks, replays the clean session with dumps at two ticks into a `.dump`, and drives every replay misuse path; CI diffs the recordings at a shared dump tick and the replayed `.dump` against the recording.

### Changed
- `TICKWISE_ABI_VERSION` is 2. The recorder config struct grew a trailing field, so a bridge compiled against version 1 must be rebuilt against the new header; every bridge in this repository checks the version at load and refuses a mismatch.
- Crate skeleton built as cdylib, staticlib, and rlib, with `unsafe_op_in_unsafe_fn` and `undocumented_unsafe_blocks` denied.
- `tickwise_ffi_abi_version` and `tickwise_ffi_version` queries, exported as `TICKWISE_ABI_VERSION`.
- `include/tickwise.h`, generated by cbindgen and checked in. CI fails when it drifts from the source.
- Release profile with fat LTO and one codegen unit. The Windows DLL links the C runtime statically, so it loads without the Visual C++ redistributable, and CI verifies its imports with `dumpbin`.
- `scripts/build-for-unity.ps1` builds the release DLL and copies it into the Unity package's plugin folder for local editor validation.
- Prebuilt binaries for Windows x86_64, Linux x86_64, Android arm64-v8a, armeabi-v7a, and x86_64, macOS universal, and iOS static, built by the Unity release workflow and attached to the `unity/v<version>` GitHub Release with the C header.
- `ctest/harness.c`, a C consumer test compiled and run by `cargo test` on Windows, macOS, and Linux. It records two sessions and drives every misuse path from C; CI reads its recordings with `tickwise inspect` and `tickwise compare`.
- The Pass 1 recorder surface: `tickwise_recorder_config_default`, `tickwise_recorder_create`, `tickwise_recorder_record_tick` with caller-provided hashes, `tickwise_recorder_wants_full_hash`, `tickwise_recorder_wants_snapshot`, `tickwise_recorder_record_snapshot`, `tickwise_recorder_record_marker`, `tickwise_recorder_finish`, `tickwise_recorder_destroy`.
- `TickwiseStatus` codes, `tickwise_last_error_message` per thread, and `tickwise_status_name`. Every call catches panics and reports them as `Panic` instead of unwinding across the boundary.
- `tickwise_xxh3_64` and the `TICKWISE_HASH_ALGO_*` constants, so engine users hash under `hash_algo_id` 1 exactly like the Rust serde layer.
